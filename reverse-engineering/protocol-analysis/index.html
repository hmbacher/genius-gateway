    Protocol Analysis¶

    Deep dive into the Hekatron Genius Plus X communication protocol structure and behavior.

    CC1101 Packet Mode Structure¶

    When the CC1101 operates in packet mode, all CC1101 packets are structured as follows. The packet format is determined by the configuration settings analyzed in the FM Basis X - RF section.

    Basic Packet Structure¶

    Based on the CC1101 configuration, each packet contains the following elements:

    Field Byte Offset Size Content Description Configuration Source
    Preamble 0-3 4 bytes 0xAAAAAAAA Synchronization sequence for clock recovery MDMCFG1[6:4] = 010
    Sync Word 4-5 2 bytes 0xD391 Packet detection pattern SYNC1=0xD3, SYNC0=0x91
    Length 6 1 byte 0x01-0x3D Payload length (N bytes, max 59)1 Variable length mode (PKTCTRL0[1:0]=01)
    Payload 7 to N+6 1-591 bytes Data (whitened) Application data with whitening applied. This section contains the Genius Plus X Packets Data whitening ON (PKTCTRL0[6]=1)
    CRC N+7 to N+8 2 bytes CRC-16 Error detection checksum over length + payload CRC enabled (PKTCTRL0[2]=1)
    Status N+9 to N+10 2 bytes RSSI + LQI Signal quality metrics appended by receiver Status append (PKTCTRL1[2]=1)

    Where N = payload length (1-59 bytes in practice)

    Packet Fragmentation¶

    The Genius Plus X system does not utilize packet fragmentation. All communication fits within the 59-byte payload limit of a single physical packet, keeping the protocol simple and energy-efficient.

    Packet limit and fragmentation

    While the CC1101 supports variable packet lengths up to 255 bytes in theory, the physical packet size is limited to 64 bytes total, including length, payload, CRC, and status bytes (but excluding preamble and sync word).

    Max. application payload = 64 bytes (max. physical payload) - 1 byte (length) - 2 bytes (CRC) - 2 bytes (status) = 59 bytes

    Packet Timing¶

    The CC1101 transmits at 38.383 kBaud with GFSK modulation:

    • Bit duration: 26.045 μs per bit
    • Byte duration: 208.36 μs per byte
    • Minimum physical packet: ~2.50 ms (12 bytes: 4+2+1+1+2+2 = preamble + sync + length + 1 byte payload + CRC + status)
    • Maximum physical packet: ~14.58 ms (70 bytes: 4+2+1+59+2+2 = preamble + sync + length + 59 bytes payload + CRC + status)
    • Typical Genius Plus packet: ~3-6 ms (15-30 total bytes including all overhead)

    Data Encoding¶

    The payload undergoes several processing steps:

    1. Data Whitening: Applied to payload (not preamble/sync) for DC balance
    2. CRC Calculation: 16-bit CRC-CCITT over length + payload
    3. GFSK Modulation: ±47.6 kHz deviation around 868.035 MHz carrier

    Genius Plus X Packets¶

    Using the parameters described in FM Basis X - RF, it is possible to build a receiver that captures and stores packets from FM Basis X modules.

    The packets documented below were received during specific functional scenarios and can be categorized accordingly.

    No Encryption

    The Genius Plus communication appears to be unencrypted. This can be observed from the serial numbers that serve as identifiers within the packets and for packet routing.

    Although not all bytes of the packet payload have been identified and understood, the evidence suggests that communication is fundamentally unencrypted, which aligns with the goal of energy-efficient communication that minimizes processing overhead.

    Message Type Byte¶

    The message body starts at offset 26 with the message family, followed at offset 27 by the message type within that family. Family and type together (with the packet length as a check) identify the packet type. The type values repeat across the families - type 0x00 exists in five of them - so the type byte alone is not enough. In the per-packet detail tables below the type is the offset-27 row (previously annotated "Unknown, seems to be constant").

    Why family and type matter for classification

    Packet length alone is ambiguous: a 36-byte frame is either a status change (0x00/0x00) or a ConfigCheckProbe response (0x55/0x08) - classifying purely by length can misread a ConfigCheckProbe response as an alarm-stop. The type byte alone is ambiguous as well: type 0x00 is the Status Change in family 0x00, the CommissioningProbe Request in family 0x66 and the daily supervision series in family 0x33, the latter two with the same length (28 B). The gateway therefore classifies on family and type with the length as a validator (type since v1.5.0, family since v1.6.0); packets of a family or type it does not know are shown as unknown.

    The ConfigCheckProbe request (0x06), response (0x08) and the 0x55 family marker at offset 26 were observed in an over-the-air capture of a Linienabschlusstest.

    Forwarding (Repeater Function)¶

    Radio modules act as repeaters: a module that receives a packet may re-broadcast it so that packets can reach modules outside the originator's direct range. Forwarding is visible on the air through two fields of the common part:

    • Hops (offset 22) starts at 0x0F on the original transmission and is decremented by one on each retransmission, limiting how far a packet propagates.
    • Fwd-SN (offset 14–17) is rewritten to the serial number of the forwarding module, while Org-SN (offset 9–12) keeps the original sender. A forwarded copy can therefore be told apart from the original: Fwd-SN != Org-SN and Hops < 0x0F.

    A packet is only forwarded when it comes from the module's own line - the line code of the originator (Org-Line, offset 8) equals the module's own line code, and the Line-ID matches or is FF FF FF FF - and the hop limit is not yet exhausted (see Line Addressing). Not every packet type is relayed: the ConfigCheckProbe and CommissioningProbe exchanges are direct-range only (never forwarded, always Hops = 0), whereas status changes (alarms, battery warnings, faults), line tests and commissioning propagate across the line.

    Whether a packet may be forwarded at all is decided by its originator: the forward class in bits 2-3 of the Flags byte (offset 24). Class 0 is never forwarded, class 1 only within the own line, class 2 within the own line and - as a collective alarm - beyond it. This matches every capture so far: the Supervision Series carries class 0 and was never seen relayed, a status change carries class 2.

    Repetition¶

    All packets are transmitted multiple times by the radio module. The packets are sent with a period of approximately 10 ms. The repeated packets are identical except for the Rem-TX (Remaining transmission time) field (see Base Packet Structure). This field starts at an individual initial value in the first packet and is decremented with each repetition until it reaches ~0, when transmission stops.

    The number of repetitions, the exact period for packet repetitions, as well as the initial value and decrementation slightly differ depending on the packet type:

    Packet Type Repetitions
    \(N\)    		 Period Time
    \(T\)    		 Initial Rem-TX
    \(RT_{Start}\)    		 Rem-TX Decrement
    \(\Delta=\frac{RT_{Start}}{N - 1}\)
    Alarm Line Commissioning 309 x ~10.06 ms 6.348 (CC 18) ~20,6
    Status Change (Alarming, Battery Low, Faults) 315 x ~9.85 ms 6.348 (CC 18) ~20,2
    Line Test (Start/Stop) 370 x ~8,40 ms 6.348 (CC 18) ~17,2
    CommissioningProbe Request 26 x ~8,19 ms 427 (AB 01) ~17,1
    CommissioningProbe Response 24 x ~9,02 ms 427 (AB 01) ~18,6
    Supervision Series 26 x not measured 427 (AB 01) ~17,1 (calculated)
    Module Missing 10 - 20 x (received) not measured 427 (AB 01) -

    Rem-TX decrement

    It can be observed that the decrement is not constant across packet repetitions but exhibits a certain amount of jitter. This is caused by the higher-resolution underlying timer (the radio module's ~2 kHz clock-tick counter): the remaining transmission time is sampled each iteration and rounded to an unsigned integer when stored in the Rem-TX field.

    Furthermore, it is notable that the average decrement approximately equals twice the period time \(T\), which corresponds to the count value of a 2 kHz clock. The initial value \(RT_{Start}\) thereby corresponds to twice the duration of the entire transmission process (across all repetitions) in milliseconds.

    Specific Packets¶

    The following section describes the structure of specific packets that were received and analyzed in connection with various Genius Plus X functions.

    Alarm Line Commissioning¶

    The packet described here occurs when functions for commissioning or establishing an alarm line are used, such as initial commissioning, when devices are subsequently added to the alarm line, and possibly other scenarios.

    Observations¶

    When commissioning is initiated via the radio module of a smoke detector that is already part of an alarm line, the stored alarm line ID is used in both the Line-ID and New Line-ID fields. This method allows new smoke detectors (i.e., corresponding radio modules that have not yet stored an alarm line ID) to be added to the existing alarm line. For this purpose, commissioning packets are responded to by all radio modules without an assigned alarm line ID, as well as only by smoke detectors (i.e. their radio modules) that have the same alarm line ID stored (i.e., are part of the initiating alarm line).

    When commissioning is initiated via a new radio module (i.e., not yet assigned to an alarm line or assignment deleted), the Line-ID field contains the value 00 00 00 00 and a generated alarm line ID is entered in the New Line-ID field. All radio modules not yet assigned (i.e., radio modules without a stored alarm line ID) signal their readiness for commissioning and, upon confirmation, store the alarm line ID proposed in New Line-ID.

    The principle by which new alarm line IDs are generated is not fully understood.

    Who takes part: line code and Line-ID state

    A commissioning packet passes the same receive filter as every other packet (see Line Addressing):

    • its line code (offset 3) is the one of the module the commissioning was started on. Only modules whose rotary switches are set to the same position accept it - an FM Basis X is always A.0;
    • of these, an unassigned module (Line-ID == 0) adopts the New Line-ID, and an assigned module reacts only to packets on its own Line-ID.

    So the rotary position has to be set before the modules are commissioned together. Earlier versions of this page said the opposite (the rotary position being metadata that is never compared); that was wrong.

    Status Change (Alarming, Battery Low, Faults)¶

    The packets described here announce a change of a smoke detector's status flags to all other smoke detectors of an alarm line. The most prominent case is the detection of smoke, which makes all smoke detectors of the alarm line signal it - the exact signaling behavior can be found in the operating instructions. The same packet also announces a low battery, device faults, radio link faults and the dismounting of a smoke detector.

    The packet carries the change as a pair of masks over the same 16-bit flag field: the flags newly set and the flags newly cleared. The flag field is the ErrorValue of Hekatron's FM.GW interface - the identical set/cleared/serial triple is forwarded 1:1 by the FM.GW serial protocol (IndNwkStateChange), which confirms the field semantics and supplies the flag names:

    Flag Name Meaning
    0x0001 Alarm Smoke detected - alarm start (set) / alarm stop or silencing (cleared)
    0x0002 Error Device fault
    0x0004 BattLow Battery low
    0x0008 Radio Radio link fault
    0x0010 Mute A radio link or dismount fault was muted (informational)
    0x0020 Dismount Smoke detector dismounted from its base

    The flags are edge-triggered: a radio module announces a flag once when it changes (computed as set = ~current & new, cleared = current & ~new) and never repeats it periodically. A gateway that misses the announcement - e.g. because it was offline - does not learn about the flag until the next change. The FM Basis X measures the battery itself: it is powered from the smoke detector's battery, so its own supply voltage is the detector battery.

    Observations (alarming)¶

    • Each smoke detector whose smoke sensor detects smoke sends a Start Alarming packet:

      • The Org-SN and Fwd-SN fields contain the serial number of the radio module of the detecting smoke detector
      • The Start field contains the value 0x01
      • The Stop field contains the value 0x00
      • The Detector field contains the serial number of the detecting smoke detector (not its radio module!)

    • Each smoke detector that receives a Start Alarming packet signals the smoke itself (acoustically and optically) and forwards the Start Alarming packet as follows:

      • The serial number of the forwarding radio module is entered in the Fwd-SN field
      • The value of the Hops field is decremented by 1

    • If the smoke sensor of a detecting smoke detector no longer detects smoke, it sends a Stop Alarming packet as follows:

      • The Org-SN and Fwd-SN fields contain the serial number of the radio module of the no-longer-detecting smoke detector
      • The Stop field contains the value 0x01
      • The Start field contains the value 0x00
      • The Detector field contains the serial number of the no-longer-detecting smoke detector (not its radio module!)

    • Each smoke detector that receives a Stop Alarming packet stops its own signaling and forwards the Stop Alarming packet as follows:

      • The serial number of the forwarding radio module is entered in the Fwd-SN field

      • The value of the Hops field is decremented by 1

        Question

        It is not known whether non-detecting but signaling smoke detectors individually store all detecting smoke detectors whose Start Alarming packets they have already received and forwarded, and only stop their own signaling when a Stop Alarming packet has been received from all detecting smoke detectors.

    • If the test button is pressed on a signaling but non-detecting smoke detector, the radio module generates a Stop Alarming packet that silences all non-detecting smoke detectors:

      • The Org-SN and Fwd-SN fields contain the serial number of the radio module of the smoke detector on which the test button was pressed
      • The Stop field contains the value 0x01
      • The Start field contains the value 0x00

      • The Detector field contains the serial number of the smoke detector (not its radio module!) on which the test button was pressed

        Tip

        Because Detector does not contain the serial number of a detecting smoke detector, another radio module receiving the Stop Alarming packet could evaluate whether it originates from a detecting or "merely" signaling smoke detector.

    • If the test button is pressed on a detecting smoke detector, the radio module generates a Stop Alarming packet that silences all smoke detectors:

      • The Org-SN and Fwd-SN fields contain the serial number of the radio module of the smoke detector on which the test button was pressed
      • The Stop field contains the value 0x01
      • The Start field contains the value 0x00
      • The Detector field contains the serial number of the smoke detector ( not its radio module!) on which the test button was pressed

    Start/Stop Mutual Exclusion

    The behavior of smoke detectors when both the Start field and the Stop field are set to 0x01 in a packet is not known.

    Start and Stop are the low bytes of the set and cleared masks - a Start Alarming packet is a status change setting the alarm flag 0x0001, a Stop Alarming packet one clearing it.

    Observations (battery low and faults)¶
    • A battery warning was captured as a status change with set = 0x0004 (BattLow), cleared = 0x0000 and the serial of the affected smoke detector in Detector - mesh-forwarded like an alarm, with Org-SN naming the radio module of that smoke detector.
    • Device faults (0x0002), radio link faults (0x0008) and dismounting (0x0020) use the same packet with their own flag; a flag that recovers is announced in the cleared mask.

    Line Test / Network Test (Start/Stop)¶

    The line test function can be used to verify or confirm the membership of smoke detectors to an alarm line. When the line test is initiated, all smoke detectors on the same alarm line as the initiating smoke detector signal their presence. The same packet starts a network test, which the manufacturer describes as the test across the whole network; the two differ in the test mode byte and in how long the detectors keep signalling. For more information on performing the line test, please refer to the smoke detector's operating instructions.

    The Line-ID field contains the ID of the alarm line for which the line test should be started or stopped.

    Line tests can be initiated or stopped from the Genius Gateway for known alarm lines. Further details can be found in Alarm Lines Management.

    Test mode byte - how line test and network test were told apart¶

    The radio modules send exactly three values in byte 28:

    Value Sent when Duration of the test
    0x04 a test is started in the first of two test states 15 minutes - as long as the commissioning mode
    0x06 a test is started in the second test state 30 minutes
    0x00 either test state is left -

    The manufacturer states that a line test lasts about 15 minutes and a network test about 30 minutes, and the serial protocol between the Genius Port and its radio module knows exactly the test modes no test, line test and network test. The two durations match, which gives the assignment above.

    • Confirmed by captures: message family 0x66, type 0x04, 29 bytes, and the test mode values 0x04 and 0x06 on air.
    • Derived, not confirmed on air: which of the two values is the line test. The assignment follows from the durations, not from a named field.

    Up to v1.5.0 Genius Gateway treated byte 28 as a start/stop flag with 0x06 as the start, and its Start Line Test action sent 0x06 - by the assignment above a network test. Since v1.6.0 it sends 0x04.

    CommissioningProbe Request¶

    This exchange runs during commissioning. After the initiating module broadcasts the Alarm Line Commissioning packet (the line assignment), it - and other involved modules - broadcast a CommissioningProbe Request, and every directly reachable module replies with a back-addressed CommissioningProbe Response (Req-SN = the requester). It is a direct-range reachability enumeration (not forwarded, Hops = 0) - a broadcast "who is reachable?" - rather than a targeted request/response. (The name reflects this observed role.)

    Observations¶

    These packets occur in connection with commissioning. Once the initiating radio module has sent the Alarm Line Commissioning Packet, these CommissioningProbe Requests are sometimes (the exact conditions are not known) additionally transmitted. In my experiments, these requests were answered with CommissioningProbe Response Packets. The radio module serial numbers contained in them did not belong to my own radio modules and were unknown to me.

    Since many residential units in my apartment complex are equipped with smoke detectors from the Hekatron Genius Plus X system, my current assumption is that the CommissioningProbe Response Packets could originate from smoke detectors (i.e. their radio modules) belonging to my neighbors. It may also specifically be their unnetworked smoke detectors, i.e., those that are installed in the base but for which commissioning (to register them in an alarm line) has not been performed.

    Furthermore, it appears that each radio module (in its own smoke detector network) that either receives the CommissioningProbe Request or is involved in the ongoing commissioning also sends the CommissioningProbe Request itself (not forwarding it, but initiating it with its own serial number). Each radio module that sent a CommissioningProbe Request itself responded to the other requests with its own CommissioningProbe Response.

    Hypothesis

    Since this packet type is not forwarded by other radio modules, only smoke detectors within direct transmission/reception range of the initiating module can respond. Thus, this part of the protocol could serve to allow smoke detectors to detect all other directly reachable smoke detectors in their vicinity.

    I do not know whether the Hekatron Genius Plus X system implements routing in any way, since I have not found any indication of an addressed recipient in the packet structure so far, but such a discovery function could serve to establish routes in such a case.

    Perhaps the mechanism is also used to prevent forwarding cycles. There is also no definitive evidence or investigation for this either.

    Radio Link Supervision (FM Pro X)¶

    FM Pro X radio modules can supervise their line: with DIP switch 5 (Funkstreckenüberwachung, off by default) switched on, the modules of a line check once a day whether all of them are still there. The manufacturer describes it like this (product information Funkmodule Basis X und Pro X für Genius Plus X, 7050611b, issue 26.06.2020):

    Jedes Funkmodul besitzt eine eindeutige Seriennummer. Bei der Inbetriebnahme speichert jedes Funkmodul die Seriennummer der Funkmodule, die zu einer Linie zusammengefasst wurden (max. 20 Funk-Teilnehmer pro Linie). [...] Die Funkstreckenüberwachung überprüft anhand der Seriennummer täglich, ob alle miteinander vernetzten Funk-Rauchwarnmelder noch vorhanden sind. Ist die Linie unvollständig, wird dies über ein akustisches Signal ausgegeben.

    The FM Basis X has no DIP switches; according to the same document all these functions are fixed to off there.

    On the air the supervision shows up as message family 0x33 with four telegrams: the daily Supervision Series, the Roll Call, the Module Missing report and the Present answer. Genius Gateway evaluates the series, the report and the present answer; its packet visualizer names the roll call Supervision Roll Call, the present answer Module Present and the line clock 0x22/0x00 Line Clock. The series, the roll call and the report were captured and analysed by danielrdt on a test line with two FM Pro X modules over 14 days (raw captures , telegram overview ). How it works describes the mechanism.

    What happens when a module goes missing¶

    Timeline of the one complete failure that was captured (one of the two modules unscrewed from its base):

    Time after the first missed series Telegram Remark
    0 - The daily series of the removed module does not come
    about 32 min 0x11/0x00 a supervision round starts (the daily check missed a member)
    + 90 s 0x22/0x00 the line clock; the module waits 89 s
    + 60 s 0x33/0x01 Roll Call the module waits 59 s; every module that hears it sends its series
    about 50 min later 0x33/0x02 Module Missing names the serial number of the missing module (check after the roll call)
    roughly 10.5 h after the first missed series 0x33/0x02 Module Missing again, 2 min later 0x11/0x01, 2 s later a Status Change with set mask 0x0008 radio link fault - the detector starts to beep (third failed round; rounds are 4 h apart)
    later, by hand Status Change, set mask 0x0010 the fault was muted on the detector

    A line does not recover by itself. After the module was screwed back in, both modules stayed silent - no series, no "fault cleared" status change. Only a new commissioning brought the daily series back. This matches the manufacturer's instruction for this fault: "Netzwerk überprüfen und Funk-Inbetriebnahme neu durchführen." The reason: a module that raises the fault switches its own supervision off - no more series, no answers to roll calls, no further reports - and the supervision never clears the fault itself (see How it works). That the re-inserted module stayed silent too fits if it had raised the fault as well while it was separated - on a line of two, each one misses the other.

    How it works¶

    Times are in seconds - two of them, 89 s and 59 s, match the captured gaps of 90 s and 60 s.

    • Members. Each module keeps up to 19 other modules (20 per line with itself), stored in its EEPROM. It learns them from the series it hears directly: a known sender is marked as heard, an unknown one is added if it is received with at least -99 dBm. Commissioning itself writes no members; the round that follows a commissioning (seen in the captures) is where the modules learn each other. Only a received series counts as heard - status changes, line tests or relayed telegrams of a module do not.
    • Daily check. Each module sends its own series - bursts for 910 s, 52 - 179 s apart, i.e. 6 - 8 bursts about 2 min apart - and then checks whether every member was heard.
    • Round. If a member was not heard: wait up to 1799 s, send 0x11/0x00, 89 s later the line clock 0x22/0x00, 59 s later the Roll Call 0x33/0x01, then its own series for 910 s. Every module that hears the roll call sends its series as well. Then check again.
    • Report. For each member still not heard: Module Missing 0x33/0x02 with its serial number, 119 s apart, then 0x11/0x01. Reporters do not coordinate: every module that misses the member reports it. A module that does hear it answers with Present 0x33/0x03 0 - 15 s later; whoever receives that and does not hear the module itself stops supervising it - the module is there, only out of its own range.
    • Retry and fault. While a member is missing, a new round starts every 4 h (14399 s). In the third failed round the module raises the radio link fault: a status change with set mask 0x0008, independent of the DIP switches, and - unless the detector has muted a fault already - the radio link error flag to its detector. With about 50 min per round this puts the reports at about 0:50, 5:40 and 10:30 h after the missed series - as captured. Raising the fault switches the module's supervision off: no more series, no answers to roll calls, no rounds 4, 5, ...
    • Clearing. The supervision never clears the fault itself. A new commissioning clears it without a status change (no cleared mask). Only a reset on the module - a short press on its button input - sends a status change with cleared mask 0x0008 (with 0x0010 if the fault was muted) and restarts the supervision.
    • FM Basis X. It never supervises its line: without DIP switches the switch mask is always 0, so DIP switch 5 is never on.

    Supervision Series¶

    Observations¶

    Module Missing¶

    A module reports that it no longer hears another module of its line, and names it by its serial number.

    Observations¶

    Other telegrams on supervised lines¶

    Three more telegrams accompany the supervision round (the fourth captured one, 0x33/0x01, is the Roll Call). Genius Gateway names 0x22/0x00 Line Clock in the packet visualizer; the family 0x11 is still shown as Unknown. It takes them as a sign of life of the sending module.

    Family / Type Length Flags Repetitions Seen Function
    0x11 / 0x00 30 B 0x48 about 350 Long burst after a commissioning and on a module failure; the two payload bytes were always B6 08. Forwarded. Opens a supervision round. B6 08 is a constant; its meaning is open.
    0x11 / 0x01 28 B 0x28 11 Twice, 2 s before the radio link fault. Sent after the last Module Missing of a round's report phase.
    0x22 / 0x00 33 B 0x08 23 About 90 s after every 0x11/0x00. Payload: hour, minute and second of the line's own clock and a 16-bit day counter. Forwarded. Sent 89 s after 0x11/0x00: distributes the line's own clock (3 clock bytes + 16-bit day counter after 22 00). Receivers presumably set their clock by it.

    The family 0x11 is not specific to the FM Pro X: FM Basis X modules can send both of its telegrams as well (0x11/0x00 with a 16-bit value, 0x11/0x01 without payload). What family 0x11 means beyond the supervision round is open.

    Line Addressing: Line Code and Line-ID¶

    A radio module belongs to its line by two values, and a packet has to match both of them:

    Line code Line-ID
    Size 1 byte 32 bit
    Comes from the two rotary switches of the module (FM Pro X, old FM Basis / FM Pro); fixed to A.0 on an FM Basis X the radio commissioning - generated there, effectively random, stored by every module of the line
    In a packet offset 3 (addressed line), 8 (originator), 13 (forwarder) offset 18–21
    Purpose separates the lines within one installation and is the basis of the collective alarm separates installations: neighbouring systems use the same rotary positions, but not the same ID

    This is what the manufacturer describes: after commissioning, a module only reacts to packets carrying both the same line and the same identification code; neighbouring systems are ignored.3

    Corrected in v1.6.0

    Up to v1.5.0 this page called the rotary position ("group/line") display metadata that the modules never compare, listed the bytes 3, 8 and 13 as an address mode and two unknown constants, and assumed that old FM Basis / FM Pro modules have no commissioned ID. All of that was wrong: the rotary position is transmitted in every packet and is part of the receive and forward filter, and old modules are commissioned by radio as well.

    Line code¶

    line code = letter << 4 | number: the high nibble is the first rotary switch (0 = A … 7 = H), the low nibble the second one (0–9).

    Rotary position Line code
    A.0 0x00
    A.3 0x03
    C.3 0x23
    H.7 0x77
    every line (Dst-Line only) 0xFF

    Seen in captures: 0x00 in all packets of FM Basis X modules, 0x03 at the offsets 3, 8 and 13 in the packets of two FM Pro X modules (see the examples under Radio Link Supervision). The same byte appears in the acoustic readout (byte 29) and in the ConfigCheckProbe response (offset 30).

    Receiving¶

    A module accepts a packet when all three conditions hold:

    1. Dst-SN (offset 4–7) is its own serial number or FF FF FF FF,
    2. Dst-Line (offset 3) is its own line code or 0xFF,
    3. Line-ID (offset 18–21) is its own Line-ID or FF FF FF FF - or the module has no Line-ID yet (0).

    A packet that fails one of them is only accepted as a collective alarm.

    Observed on a line of eleven FM Basis X modules (line code 0x00): a line test start addressed to its Line-ID made all detectors signal and was forwarded by the modules. The same packet with the line code 0x01 (A.1) at the offsets 3, 8 and 13 - flags and everything else unchanged - left every detector silent, and no module forwarded it. The following stop with the line code 0x00 was forwarded by all of them.

    Forwarding¶

    A module forwards a packet of its own line: Org-Line (offset 8) equals its own line code and condition 3 above holds. On forwarding it writes its own line code and serial number into Fwd-Line and Fwd-SN. Forward class and hop limit apply as described under Forwarding; a packet of another line is only forwarded as a collective alarm.

    Collective alarm lines¶

    The letter H stands for the collective alarm lines (Sammelalarm; FM Pro and FM Pro X only). A module with DIP switch 4 (Receive Collective Alarm) switched on also accepts and forwards packets of other lines, if the packet carries the collective bit (bit 4 of Flags, offset 24) and the two line codes are paired:

    Collective line Paired with
    H.0 A, B
    H.1 C, D
    H.2 E, F
    H.4 A, B, C
    H.5 D, E, F
    H.7 A – G and H.0, H.1, H.2, H.4, H.5
    • The pairing works in both directions: a module on a line A.x accepts collective packets from H.0, H.4 and H.7.
    • For the lines A – G only the letter counts here, not the number.
    • H.3, H.6, H.8 and H.9 are paired with nothing.
    • The Line-ID is not compared for a collective packet.

    Collective packets were not captured so far; nothing of this was verified on air.

    FM Basis X¶

    • No rotary switches: the line code is permanently 0x00 (A.0). No DIP switches either, so no collective alarm.
    • It follows that FM Basis X modules only work together with modules whose rotary switches are set to A.0 - the manufacturer's rule for mixed operation with old modules.3
    • Over smartsonic acoustic readout, bytes 25–28 carry the commissioned 32-bit lineId (non-zero once commissioned; 0 = unassigned) and byte 29 the line code.

    Old generation - FM Basis and FM Pro¶

    • Two rotary switches (letter A–G/H, number 0–9; the manufacturer speaks of up to 70 lines). Factory default is A.0.
    • The modules are commissioned by radio as well, and the commissioning gives them a 32-bit Line-ID. Reported for an installation with FM Pro modules and a used FM Basis from 2014 (#33):
      • A module that is inserted with its rotary switches set like those of the others (A.1) does not join their line. Its Line-ID is 0 ("not set"), and it starts a commissioning of its own.
      • A commissioning started on a detector that already belongs to the line takes new modules into that line: they adopt its Line-ID. A commissioning started on a new detector opens a new line with a new Line-ID - with the rotary switches unchanged.
      • So the rotary position alone does not make a line. As on the X generation, both values count.
    • Over smartsonic, an old module transmits only its type and serial number - not the radio dataset. The acoustic lineId (bytes 25–28) reads 0. The Line-ID of an old module is therefore only visible on air, in the packets it sends.
    • Open: whether old modules carry their line code at the offsets 3, 8 and 13 like the X generation was not checked against a capture yet.

    What the gateway makes of it¶

    • Receiving. The gateway listens to every packet, whatever its line code and Line-ID. It keys alarm lines on the Line-ID. The line code of the originator (Org-Line) gives the line setting of a detector with an FM Pro X or a module of unknown type, and of an alarm line that is added from the packet or whose detectors do not tell it - never from a packet originated by a gateway. The packet visualizer shows all three line codes.
    • Alarm line of a detector. It is taken over from the radio packets of its module: an alarm, a status change, a line test or a telegram of the radio link supervision names the Line-ID. For old modules that is the only source, see Device Management. Their rotary position is entered by hand.
    • Transmitting. Line test, fire alarm and commissioning packets of the gateway carry the line setting of the alarm line at the offsets 3, 8 and 13. Up to v1.6.0 it was always 0x00 (A.0), and by the receive rule above modules set to another rotary position did not accept them - observed with the line code the other way round: a line test start with the line code 0x01 was ignored by a line set to A.0 (see Receiving). It fits the report in #33 that a commissioning started by the gateway had no effect on a line set to A.1. The range test is not affected: its ConfigCheckProbe addresses every line.
    • Old modules were observed not to answer the ConfigCheckProbe of the range test.
